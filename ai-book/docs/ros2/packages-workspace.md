# ROS 2 Packages and Workspace Structure

In ROS 2, code organization is critical for managing complexity, fostering reusability, and facilitating collaboration. This chapter explores the concepts of ROS 2 packages and workspaces, which are fundamental to structuring your robotic software projects.

## 1. ROS 2 Packages

A **ROS 2 Package** is the primary unit of software organization in ROS 2. It's a directory that contains a collection of source code (C++, Python), build scripts, configuration files, launch files, message definitions, and other resources related to a specific piece of functionality.

Key aspects of a ROS 2 package:

*   **`package.xml`**: Every ROS 2 package must contain a `package.xml` file. This manifest file provides metadata about the package, including its name, version, description, maintainers, license, and most importantly, its **dependencies**.
*   **Build System Integration**: Packages are integrated with the `ament` build system (which uses CMake for C++ and setuptools for Python) to ensure they can be compiled and installed correctly.
*   **Modularity**: Packages promote modularity by encapsulating related functionalities, making it easier to share, reuse, and manage code.
*   **Naming Conventions**: Package names are typically lowercase, use underscores to separate words, and should be unique within a ROS 2 system.

**Typical Package Structure**:

```text
my_ros2_package/
├── CMakeLists.txt     # CMake build instructions (for C++ packages)
├── package.xml        # Package manifest
├── src/               # Source code (e.g., C++ files, Python scripts)
│   ├── my_node.cpp
│   └── my_python_node.py
├── include/           # Header files (for C++ packages)
│   └── my_ros2_package/
│       └── my_header.hpp
├── launch/            # Launch files (e.g., .launch.py, .launch.xml)
│   └── my_launch_file.launch.py
├── config/            # Configuration files (e.g., .yaml, .json)
│   └── my_params.yaml
├── messages/          # Custom message definitions (e.g., .msg, .srv, .action)
│   └── MyMessage.msg
└── test/              # Test files
    └── test_my_node.cpp
```

## 2. ROS 2 Workspaces

A **ROS 2 Workspace** is a directory that holds a collection of ROS 2 packages, allowing them to be developed, built, and installed together. Workspaces provide a structured environment for managing your robotics projects.

### Types of Workspaces

*   **Source Workspace**: Contains the source code of your ROS 2 packages. This is where you actively develop your packages.
*   **Install Workspace**: Contains the compiled binaries, libraries, and other installable artifacts of your packages after they have been built.
*   **Overlay Workspace**: A common practice in ROS 2 is to create an "overlay" workspace. This means your development workspace builds on top of an existing ROS 2 installation (e.g., from a binary distribution like `ros-humble-desktop`). Packages in your overlay workspace will override or extend packages from the underlying installation.

### Workspace Structure

A typical ROS 2 workspace (source workspace) has the following structure:

```text
my_ros2_ws/          # Your workspace directory
├── src/             # Source space: Contains your ROS 2 packages
│   ├── my_package_a/
│   │   └── package.xml
│   └── my_package_b/
│       └── package.xml
├── install/         # Install space: Generated by the build process
│   └── my_package_a/
│   └── my_package_b/
├── log/             # Log space: Contains build and test logs
├── build/           # Build space: Intermediate build files
```

### Managing Workspaces with `colcon`

**`colcon`** is the primary command-line tool used to build, test, and install multiple ROS 2 packages in a workspace. It's an improvement over `catkin` from ROS 1, offering greater flexibility and better support for mixed language projects.

**Key `colcon` Commands**:

*   **Initializing a Workspace**:
    ```bash
    mkdir -p my_ros2_ws/src
    cd my_ros2_ws
    colcon build
    ```
    This command will create the `install`, `log`, and `build` directories if they don't exist, and perform an initial build (even if `src` is empty).

*   **Building Packages**:
    ```bash
    cd my_ros2_ws
    colcon build
    ```
    This command builds all packages in the `src` directory. You can build specific packages using `colcon build --packages-select package_name`.

*   **Sourcing the Environment**: After building, you need to "source" the workspace's setup files to make its packages and executables available in your shell environment.
    ```bash
    source install/setup.bash  # For Bash
    source install/setup.zsh   # For Zsh
    source install/setup.ps1   # For PowerShell
    ```
    It's common to add this `source` command to your `.bashrc` or equivalent shell configuration file.

*   **Cleaning a Workspace**:
    ```bash
    rm -rf build install log
    ```
    This command removes the build, install, and log directories, effectively cleaning the workspace.

## Conclusion

A well-structured ROS 2 project relies heavily on the proper use of packages and workspaces. By understanding how to define packages with `package.xml`, organize them within a workspace, and manage them with `colcon`, you can efficiently develop and maintain complex robotic applications.
