# Research: Book Layout + Docusaurus Setup

**Feature Branch**: `001-docusaurus-book-layout`
**Created**: 2025-12-04
**Purpose**: Resolve design decisions related to Docusaurus layout, folder structure, and navigation based on the Context7 Dinosaurs example.

## Decisions Needing Documentation

### Folder Naming Conventions for Modules and Subchapters

**Decision**: Modules will be top-level directories under `docs/` (e.g., `docs/ros2`, `docs/gazebo-unity`), with an `index.md` file for the module overview. Subchapters will be Markdown files directly within their respective module directories (e.g., `docs/ros2/introduction.md`).
**Rationale**: This approach leverages Docusaurus's file-system based routing for clarity and automatically generates a logical URL structure. Using `index.md` for module overviews is a common and clean pattern.
**Alternatives Considered**:
- Nested subdirectories for chapters (e.g., `docs/ros2/chapter1/introduction.md`): Rejected for simplicity in this initial iteration, aiming for a flatter structure unless chapter complexity demands deeper nesting.

### Sidebar Grouping Strategy for Modules

**Decision**: Autogenerated sidebars will be used for each module directory (`docs/ros2`, `docs/gazebo-unity`, etc.), combined with explicit category definitions in `sidebars.js` to provide custom labels and control the order of modules and their subchapters.
**Rationale**: Autogenerated sidebars simplify maintenance as new chapters are added, while explicit category definitions offer the flexibility to customize display names and ensure a logical flow in the navigation. This aligns with Docusaurus best practices for scalability and customizability.
**Alternatives Considered**:
- Fully manual sidebar configuration: Rejected due to potential for boilerplate and increased maintenance burden as the book grows.
- Only autogenerated sidebars: Rejected because it offers less control over display names and explicit ordering, which is important for a structured textbook.

### Placement of Homepage vs. Docs Index

**Decision**: The homepage will be a custom React component located at `src/pages/index.js`. The main documentation content will start at the `/docs` route, with a dedicated `docs/index.md` or similar file serving as the entry point to the documentation section.
**Rationale**: This separation allows for a rich, branded landing page (`src/pages/index.js`) for the book that can be customized independently of the documentation content. The `/docs` route provides a clear, consistent entry point for navigating the technical content, adhering to standard Docusaurus practices.
**Alternatives Considered**:
- Using `docs/index.md` as the main homepage: Rejected as it limits the flexibility and dynamic capabilities of the landing page, which is desirable for introducing an AI-native textbook.

### Routing Structure for Future Chapters

**Decision**: Docusaurus's file-system based routing will be used. For future chapters, new Markdown files will be created directly within their respective module directories (e.g., `docs/ros2/advanced-topics.md`), extending the existing pattern. An `index.md` file will continue to serve as the landing page for each module.
**Rationale**: This approach is straightforward, maintainable, and automatically generates clear URL paths (e.g., `/docs/ros2/advanced-topics`). It aligns with Docusaurus's core design philosophy and ensures consistency across the book.
**Alternatives Considered**:
- Custom programmatic routes via plugins: Rejected as unnecessary for standard chapter content and adds complexity that is not required at this stage.
- Nested directories for individual chapters within a module: Rejected for this iteration to keep the initial structure flatter, but remains a viable option for highly complex chapters in future iterations.

### Markdown Formatting Consistency for Upcoming Iterations

**Decision**: Markdown content will adhere to GitHub Flavored Markdown (GFM) and MDX syntax, as supported by Docusaurus. To ensure consistency, a project-specific Markdown style guide will be established, and tools like Prettier (for formatting) and potentially ESLint (for MDX files, with markdown plugins) will be configured.
**Rationale**: Relying on GFM and MDX ensures compatibility and leverage Docusaurus's native capabilities. Implementing a style guide and automated formatting tools will enforce consistency across multiple contributors and iterations, improving readability and maintainability.
**Alternatives Considered**:
- No explicit style guide or automated tools: Rejected as this would lead to inconsistencies and potential formatting issues as more content is added.
- Strict adherence to a pre-existing external style guide without customization: Rejected to allow for project-specific nuances and the ability to define custom rules where necessary for the textbook's unique content.
